Surf Ace Native Pane Window Groups Requirements

Amended 2026-09-01

Authority: T368 decision dr_eddcae41-3f78-4d3a-aa19-7be09abe6d47, plus Mike's 2026-09-01 clarification that focus-gated hiding is not surface disappearance.

A launched native GUI app may create dialogs, palettes, popups, and tool windows. Surf Ace keeps those accessory windows in the app's pane-owned window group, but it does not confine them to the pane rectangle.

Focus-gated visibility is the containment mechanism. Exactly one pane has keyboard focus. Surf Ace identifies that pane visually. Only the accessory windows of the focused pane are visible.

Product Goal

Model

A native pane owns a physical window family. It is not a global desktop or a single-surface slot.

Placement

Accessory windows may float outside their pane, over other panes, and over Surf Ace chrome.

Containment

Only the focused pane's accessory windows are visible. Blur hides them without destroying them.

Proof

Real packaged GUI apps must pass through the official Surf Ace provider and materialization path on Racter and Shrdlu.

Focus and Overlap Model

StateMeaningInput Consequence
Pane focusSelects the one pane whose native group may show accessories and receive keyboard input.Surf Ace always shows one unambiguous focused-pane indicator.
Surface focusSelects the primary surface, accessory, or Surf Ace recipient inside the focused pane context.The disappearance fallback returns surface focus to Surf Ace without erasing the focused-pane invariant.
Overflow overlapA visible accessory may cover another pane or Surf Ace chrome.The topmost visible accessory wins hit-testing at covered pixels. An exposed pane region or explicit Surf Ace focus affordance changes pane focus.

Accessory overlap must not make the required focused-pane indication ambiguous. The implementation may choose its layering or location.

Lifecycle Boundary

EventRequired State ChangeForbidden Interpretation
Owning pane loses focusHide every accessory window in that pane group. Preserve each surface, group identity, position, size, z-order, focus history, application state, and restoration state.Do not close, destroy, cancel, or treat the hidden surface as missing.
Owning pane regains focusRestore every still-existing accessory at its prior position, size, z-order, and application state. Reapply group-local focus according to the preserved state.Do not relaunch or reconstruct the windows as new surfaces.
App destroys an accessory while it is hiddenRecord the genuine lifecycle change and remove that member from restoration state.Do not synthesize a replacement or claim that refocus restored it. Do not invoke interaction cancellation unless an active interaction actually existed.
Native content genuinely disappears during an active interactionApply dr_595d4764-a089-4345-8167-6b3df807f5f2: cancel the interaction, record a durable diagnostic, and return subsequent focus and input to Surf Ace.Do not redirect the interaction to another pane or app.

The disappearance fallback never runs solely because focus-gated policy hid a still-existing window.

Requirements

IDRequirementAcceptance
R1Represent each native pane as a NativePaneWindowGroup or equivalent model with one primary toplevel and zero or more accessory toplevels or popups.Status enumerates stable member ids, roles, bounds, z-order, focus, visibility, hidden reason, and lifecycle.
R2Classify secondary toplevels from the same launched process tree or launch token as members of the launching pane group.A KolourPaint dialog or tool window joins the same group and is not closed as an unknown global toplevel.
R3Reject or close toplevels that cannot be tied to the pane launch identity.Status records a denied count and reason for every foreign or unowned toplevel.
R4Allow accessory windows to move, resize, and render outside the owning pane, including over other panes and Surf Ace chrome.A dialog crosses each pane edge without clipping or edge clamping. Capture shows its actual bounds and pixels. The topmost visible accessory receives input at covered pixels.
R5Maintain pane-group z-order and group-local activation for primary, dialog, palette, popup, and tool windows.Clicking an accessory raises and focuses it within the focused pane group without changing group ownership.
R6Maintain exactly one keyboard-focused pane and show an unambiguous Surf Ace focus indicator.Every pane-focus transition has one focused pane, one visible focus indication, and deterministic input ownership. Accessory overlap never obscures the focus truth.
R7Show accessory windows only for the focused pane. Hide all accessories of every unfocused pane, including accessories that fit within the pane. Keep each pane's primary content visible.Focusing another pane hides the prior pane's dialogs, palettes, popups, and tool windows without hiding its primary content. The newly focused pane's still-existing accessories become visible.
R8Treat focus-gated hiding as visibility only for surfaces that still exist.After blur and refocus, every still-existing accessory restores with the same surface identity, position, size, z-order, and app state. A surface genuinely destroyed while hidden remains destroyed and is reported. No close, relaunch, or disappearance fallback occurs solely because of blur.
R9Route pointer and keyboard input only through the active focus, z-order, and visibility state, translated into the target window's local coordinates.The topmost visible accessory wins at overlapping pixels. Hidden accessories receive no input. Clicking an exposed region of another pane or an explicit focus affordance transfers pane focus before that pane's accessories accept input.
R10Apply the cancel-and-return fallback only when native content genuinely ceases to exist during an interaction.A destruction test cancels the interaction, records a durable diagnostic, and returns subsequent focus to Surf Ace. A blur test does none of those things.
R11Expose diagnostics that distinguish visible, focus-hidden, closed, rejected, and genuinely disappeared surfaces.get_status and Surf Ace tool state prove the pane owner, group members, focused pane, visible accessories, hidden reason, preserved restore state, destroyed-while-hidden state, and denied counts.
R12Use packaged real GUI apps and the official Surf Ace launch and materialization path as product proof.Direct compositor injection and demo state are excluded from the acceptance record.
R13Keep terminal and simple single-window apps working as one-member pane groups.Existing one-window behavior remains green under the new focus model.
R14Avoid persistent service, launchd, systemd, or auto-start changes unless separately authorized.Implementation and proof remain test-scoped unless deployment persistence receives explicit approval.

Non-Goals

IDNon-Goal
NG1Do not create a global desktop, task switcher, workspace system, or general window manager.
NG2Do not clip accessory windows to the pane rectangle or clamp their movement to pane edges.
NG3Do not use pane confinement as the containment mechanism.
NG4Do not treat a focus-hidden window as closed, destroyed, missing, or relaunched.
NG5Do not accept direct compositor or native-pane hosting as product proof.
NG6Do not solve arbitrary cross-app drag and drop, clipboard behavior, or session restore unless the window-group implementation requires it.

Pane Target Restore Boundary

The first slice covers launch-time and runtime window-group behavior. It does not promise child-window persistence across an explicit pane target restore.

Target restore is a controller-driven lifecycle transition, not focus blur. If it ends a native group, status must report the resulting lifecycle changes. The implementation must not reuse blur-hiding to disguise closure, or reuse closure to implement ordinary blur.
